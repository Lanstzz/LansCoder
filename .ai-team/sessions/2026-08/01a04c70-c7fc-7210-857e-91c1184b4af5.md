## 三、问题清单（按"收益/成本"排序）

### P1 每次请求全量重放会话，长会话性能 O(n²)【性能，最痛】

`Session.rebuild_view()`（`/Users/lansterzhang/Documents/LansCoder/lanscoder/agent/session.py:528`）直接调 `store.rebuild_session_view()`——**把整个 JSONL 从头逐事件重放一遍**。而它在 `_prepare_main_provider_request` 里**每个工具轮次都调用**（`/Users/lansterzhang/Documents/LansCoder/lanscoder/agent/loop.py:562/584/624`），runtime 层还有多处（`/Users/lansterzhang/Documents/LansCoder/lanscoder/core/runtime.py:350/360/383/389`）。

更糟的是持久化侧：`append_event` 里每次事件都触发 `SessionIndex.update_event`（`/Users/lansterzhang/Documents/LansCoder/lanscoder/session/index.py:24`），它会**重新读取整个会话 JSONL 再重写整个 index 文件**。所以一个 N 事件的会话，光持久化簿记就是 O(N²) 的读+写。

对照：Claude Code / Aider 都维护**内存中的增量会话状态**，落盘是旁路。LansCoder 的事件溯源是正确架构，但缺了"内存增量视图 + 脏标记 + 落盘解耦"这层。

### P2 token 估算用 `(len+3)//4` 启发式，对代码和中文严重失真【正确性】

`estimate_text_tokens`（`/Users/lansterzhang/Documents/LansCoder/lanscoder/context/token_budget.py`）是字符数/4。后果：
- **中文**：主流 tokenizer 里中文字符约 1–3 token/字，`chars/4` 是 0.25 token/字 → **低估 4–12 倍**。对一个中文用户为主的 agent，压缩水位（90%/72%）全部基于错误计量，可能迟迟不压缩然后直接撞 `PROMPT_TOO_LONG`。
- **代码/JSON**：符号密集，同样失真。

更关键的连锁问题：`ProviderCapabilities`（`/Users/lansterzhang/Documents/LansCoder/lanscoder/providers/types.py:33`）**没有 context_window 字段**，`DEFAULT_CONTEXT_WINDOW=200_000` 是拍脑袋的 `assumed` 值。模型换小窗口时整个水位体系失效。

对照：Claude Code 按模型 ID 查表 + 真实 token 计数（`/context` 还能按类别给出真实占用）；Aider 用 tiktoken 精确计数决定 repo map 预算。

### P3 没有代码库级上下文：无 repo map / 符号索引 / 检索【能力缺口，影响大仓表现】

全仓 grep 不到任何 `repo_map / tree-sitter / symbol_index / bm25`。模型只能靠 `view/grep/glob` 自己探索，且每次探索的结果都经过"读进来→生命周期失效→归档"的循环，反复进出上下文。

对照成熟方案：
- **Aider**：tree-sitter 解析 + 符号 PageRank 排序，按 token 预算（约 `min(1024, max_input/8)`）二分注入 repo map，编辑后对应符号失效。
- **Cursor**：代码库索引（embedding + Merkle 树增量同步），`@codebase`/dynamic context discovery 按需取文件。
- **Claude Code**：文件按需读 + 路径作用域规则，压缩后恢复最近 5 个文件。

LansCoder 缺的是"**让模型一开始就知道仓库里有什么**"这一层，它是所有 coding agent 上下文管理的起点。
