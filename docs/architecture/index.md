# 架构总览

> LansCoder 架构导览。本文先给全局地图与分层规则，后续各篇深入每一层：`01-编排层`、`02-能力层`、`03-模型与上下文`、`04-会话与扩展点`。

LansCoder 是一个约 2.9 万行 Python 的终端 AI 编程代理。它的核心设计承诺是：**系统真实可用，同时小到可以通读**——每个子系统都有明确的存在理由，层与层之间的依赖方向被测试锁定。

## 为什么分层

单一平面式的代码在功能堆叠后必然走向循环依赖与"谁都可以 import 谁"的泥潭。LansCoder 用**严格分层**来保持可读性：

1. **可读性**：每一层只回答一个问题（如何展示、如何编排、如何执行、如何持久化）。
2. **可检查性**：依赖方向单向，读代码时可以确定"这个模块能影响谁、被谁影响"。
3. **可测试性**：层间通过抽象（Protocol）交互，测试可以替换真实实现。

## 模块地图

15 个顶层模块，按职责分四层：

| 层 | 模块 | 一句话职责 |

| 基础设施 | `memory/` | 跨会话持久记忆（项目级 / 用户级） |

## 四层架构

### 1. 表现层 `app/`

Textual 构建的终端 UI。它**不包含业务逻辑**：用户输入在这里被收集，模型输出在这里被渲染，权限确认在这里被展示。表现层依赖编排层（调用 `ChatRunner`），但编排层完全不感知 UI 的存在——这是它能同时支撑 TUI、REPL 与单次运行三种前端的原因。

### 2. 编排层 `agent/`

整个系统的**大脑**。代理循环（`loop.py`）驱动一个回合：构造请求 → 调用模型 → 执行工具 → 结算结果 → 循环直至完成。编排层同时持有权限协调器（`PermissionCoordinator`）作为**单一执法闸门**，所有工具的权限检查都在这里完成，而不是散落在各个工具里。

### 3. 能力层 `tools/` + `permissions/`

这一层是 LansCoder 最核心的设计：**工具与权限互不知晓**。

- `tools/` 只关心"如何执行"：每个工具声明自己的参数、执行逻辑、结果格式。
- `permissions/` 只关心"能否执行"：策略决定某个操作该放行、拒绝还是询问。
- 二者通过编排层的 `PermissionCoordinator` 桥接——工具发起请求，协调器按权限策略裁决，工具不知道策略的存在，权限也不知道工具的实现。

这带来两个直接好处：新增工具不需要碰权限代码；权限策略调整不需要改任何工具。`lanscoder.tools` 被测试锁定为**永不 import `lanscoder.agent`**（见下文门禁）。

### 4. 基础设施层

横切组件，为上层提供可复用的能力：

- `providers/` 把不同模型服务统一成 `ChatProvider` 接口（流式/非流式）。
- `context/` 记录全部事件、构建模型输入、在超预算时压缩。
- `session/` 管理会话的创建/恢复/分支/分享，JSONL 持久化。
- `mcp/`、`memory/`、`skills/`、`planning/` 等是扩展点，被编排层通过抽象接入。

基础设施层**不知道**表现层与编排层的存在；编排层通过 Protocol 依赖它们，可以在测试中替换。

## 依赖规则与门禁

依赖方向**单向向下**：表现层 → 编排层 → 能力层 → 基础设施。上层可以依赖下层，下层不得依赖上层；同层模块通过抽象交互。

这条规则不是纸面约定，而是被测试锁定的（`tests/test_layer_boundaries.py`）：

- **`lanscoder.tools` 永不传递性 import `lanscoder.agent`**：历史上 `delegate` 工具曾依赖 `agent.subagent_engine`，形成 `agent → tools → agent` 的循环依赖，只能靠函数级惰性 import 苟活。测试在**全新解释器**里 import `lanscoder.tools`，断言 `sys.modules` 中没有 `lanscoder.agent` 的任何模块——从根上杜绝回归。
- **`agent.loop` 不 import `agent.subagent_engine`**：子代理引擎通过装配根注入的 `child_runner_factory` 获取循环能力，而不是反向 import，打破 `loop → subagent → loop` 的历史循环。
- **`permissions.classification` 禁止 import tools / agent / app**：权限分类表是外置的，不感知工具实现。

此外还有包级边界测试（`tests/test_session_package.py`），验证 `session/` 等模块在**没有 Textual 依赖**的环境下也能独立工作。

> 这套门禁的设计哲学：**循环依赖一旦出现就很难消灭**，与其靠纪律，不如用测试把边界钉死。新增模块时先问自己：它属于哪一层，依赖方向是否单向？

## 一次用户回合的旅程

以 TUI 中输入一条指令为例：

```
用户输入 "读 README 并总结"
   │
   ▼
[表现层 app/]  收集输入，交给 ChatRunner
   │
   ▼
[编排层 agent/loop]  构造请求（消息 + 工具定义 + 系统提示）
   │
   ▼
[基础设施 providers/]  调用模型 API（流式/非流式）
   │
   ▼
[编排层 agent/loop]  解析响应；若模型请求调用工具：
   │                 进入工具流（tool_flow）
   ▼
[编排层 PermissionCoordinator]  对工具调用做权限裁决
   │                           放行 / 拒绝 / 询问用户
   ▼
[能力层 tools/]  执行工具（读文件、编辑、跑命令…）
   │
   ▼
[编排层 agent/loop]  把工具结果作为消息，继续下一轮
   │
   ▼
[基础设施 context/]  记录事件、检查上下文预算、必要时压缩
   │
   ▼
[基础设施 session/]  全部事件 JSONL 持久化
```

完整时序在 [01-编排层](01-orchestration.md) 展开。

## 设计取舍

- **工具与权限解耦**：牺牲了"工具内直接声明权限"的便利，换来权限策略的集中与可审计。
- **单一执法闸门**：所有权限检查经 `PermissionCoordinator`，避免"有的工具检查、有的不检查"的漏网。
- **事件溯源式持久化**：会话是 JSONL 事件流，而非数据库行——恢复、分支、重放都基于事件重建，天然可审计。
- **分层而非微服务**：保持单进程内可通读，用测试锁边界而非用进程隔离。
